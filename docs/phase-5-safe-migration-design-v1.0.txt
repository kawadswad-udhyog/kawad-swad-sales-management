1. PHASE 5 PURPOSE
The Business Database Blueprint defines Phase 5 as safe migration design:
per-change mapping, affected records, backup, dry-run, validation and
rollback design approved before implementation.

This plan preserves the Owner's clean-empty-database direction:
- Google Sheets remains the authoritative business record.
- FastAPI implements business logic and API validation.
- MongoDB is optional cache/processing, never the sole business source.
- Do not restore, recover, import or seed pre-reset business records.
- Do not perform live sheet/header/tab/ID changes in Phase 5 design work.

4. MIGRATION CHANGE CLASSES
CLASS 0 - READ-ONLY OBSERVATION
Inventory, checksums, counts, mappings and diagnostics. Permitted now.

CLASS 1 - APPLICATION-ONLY COMPATIBILITY
Explicit header aliases, strict validation, fail-closed writes and read-back.
Development branch and sandbox only; production needs separate release
approval.

CLASS 2 - ADDITIVE SHEET SCHEMA
Only individually approved fields/tabs with business reason, route mapping,
backup, dry-run and rollback. Design only; not executable now.

CLASS 3 - DESTRUCTIVE / STRUCTURAL
Rename, reorder, delete, merge, archive, replace data. Not authorized.

CLASS 4 - BUSINESS DATA RESTORE / IMPORT / BACKFILL
Historical business data or IDs. Explicitly excluded by the clean-empty
database direction. No execution planned.

CLASS 5 - ID / FOREIGN-KEY ENFORCEMENT
Design and isolated tests only until generator inventory, uniqueness,
parent-key proof, concurrency and retry behavior pass.

6. FIELD-LEVEL DECISION RULES
- Exact match: preserve; verify route read/write and semantics.
- Alias: map API field to physical header; do not duplicate the column.
- Missing mandatory field: block the operation until approved and supported.
- Proposed unused field: do not create a column without workflow approval.
- Legacy field: retain values and consumers until mapped and approved.
- Duplicate semantic field: do not merge automatically.
- Type review: no bulk conversion; test values, units, money precision and
  date/time interpretation in a sandbox.
- Not applicable: document reason and waiver; do not silently delete.

Every per-field ticket must identify table, canonical and physical field,
route reads/writes, frontend/Apps Script consumers, type/unit, requiredness,
unique/reference rules, sensitivity, affected rows, decision, approvers,
sandbox result, rollback and post-migration verification.

7. BACKUP / DRY-RUN / ROLLBACK
Before a production migration, record:
- Exact workbook ID and title.
- Fresh export timestamp and SHA-256.
- Sheet inventory, headers and actual non-empty record counts.
- Formulas, validations, protections, named ranges, triggers and scripts.
- Backend commit and Render deployment record.
- Backup location, access list and restore-test result.

Dry-run must report:
- Source/target field and proposed operation.
- Actual affected records.
- Header and ID effects.
- Uniqueness/reference conflicts.
- Type conversion exceptions.
- Formula/script/API dependencies.
- Financial and inventory before/after totals.
- Warnings, stop conditions and rollback.
No dry-run may write to the live workbook.

Rollback:
- Application-only: restore the previous approved code/config and reconcile
  pending operations.
- Additive schema: disable new code path; retain unused columns; do not
  delete potentially populated columns.
- Posted stock/finance: linked reversal/adjustment, never overwrite history.
- Uncertain transaction: mark review-required and reconcile before retry.
- Restore tests use a disposable workbook only, never the live workbook.
