1. VERIFIED SOURCE FINDINGS

PRODUCTS
- Routes: GET/POST /api/products; PUT/PATCH /api/products/{product_id}.
- GET returns product_id, sku, product_name, category, variant, pack_weight_g, selling_unit, retail_pack_only, recipe_id, active, notes.
- POST permitted to OWNER, OWNER_ADMIN, PA. It allocates a product ID before any SKU duplicate check (no duplicate SKU check currently exists).
- POST writes the 10 physical fields and optionally recipe_id.
- Physical Products headers are 10 fields; recipe_id and created_at/created_by/updated_at/updated_by are absent.
- sheets.py REQUIRED_TABS for Products declares exactly the existing 10 headers.
- append_record silently omits fields not present in physical headers unless header update is explicitly authorized. Consequently recipe_id is omitted from persistent rows.
- POST does not persist created_at/created_by. PUT/PATCH does not persist updated_at/updated_by.
- Recommendation: one Products row per sellable SKU/pack, pending Owner approval.

CUSTOMERS
- Routes: GET/POST /api/customers; PUT /api/customers/{customer_id}.
- Any authenticated user can currently list/create/update; no route-specific sales/accounts/Owner scope is present in these handlers.
- GET exposes shopkeeper name, mobile, alternate mobile, address, city, GSTIN, map location and notes to any authenticated user.
- POST writes customer_id, customer_type, shop_name, shopkeeper_name, mobile, alternate_mobile, address, locality_area, city, gstin, map_location, active, created_at, notes.
- Physical Customers headers are 14 fields and include notes and GSTIN.
- sheets.py REQUIRED_TABS declares 13 fields and omits notes; it does not declare created_by, updated_at or updated_by.
- Current route writes notes; the physical sheet accepts it. The required-header contract therefore does not fully reflect actual use.
- Current API defaults city to Bhilwara.
- Pydantic Customer response model includes credit_limit, max_overdue_days and current_balance defaults, but these are not part of physical Customers headers nor Phase 1 Customers dictionary. Routes do not persist them. Do not treat defaults as authoritative balances/credit limits; source those from approved customer-ledger/credit-control tables.
- Create has no duplicate/possible-duplicate detection. Update is full-model replacement, not partial update; no updated_at/updated_by.

SUPPLIERS
- Routes: GET/POST /api/purchasing/suppliers; PUT /api/purchasing/suppliers/{supplier_id}.
- Endpoints require purchasing access.
- SupplierCreate fields: supplier_name, contact_person, mobile, email, address, city, gstin, notes.
- POST allocates supplier_id before duplicate-name validation.
- City defaults to Barwani.
- POST/PUT does not use payment_terms_days or opening_balance.
- Physical Suppliers has 14 headers and includes payment_terms_days/opening_balance.
- Phase 1 Suppliers dictionary proposes updated_at/updated_by and omits payment_terms_days/opening_balance.
- Important correction: current main backend sheets.py REQUIRED_TABS does NOT declare a Suppliers entry, even though the Phase 1 table registry marks Suppliers as having a backend contract. This must be resolved before any installer/preflight relies on REQUIRED_TABS.
- PUT does not persist updated_at/updated_by.
- Supplier-name duplicate check is lowercase/trimmed but no GSTIN validation or duplicate handling is visible.

RAWMATERIALS
- Routes: GET /api/production/raw-materials; POST /api/production/raw-materials/receive; POST /api/production/raw-materials/verify-opening-stock.
- GET requires production access; it reads RawMaterials and RawMaterialLedger, calculates balances, but falls back to RAW_MATERIALS_SEED if master is empty and appends missing seed items to the returned API list.
- Receive requires production access but, if no real master record is found, searches RAW_MATERIALS_SEED and may append a new RawMaterials master row automatically.
- Opening-stock verification is Owner-only but also uses RAW_MATERIALS_SEED fallback.
- No ordinary explicit RawMaterials master create/update route was identified. Master creation is currently coupled to the receive fallback.
- sheets.py REQUIRED_TABS for RawMaterials declares nine headers: raw_material_id, material_name, current_stock, unit, rate_per_unit, rate_status, category, created_at, created_by.
- Physical RawMaterials has 13 headers, including opening_stock, minimum_stock, active and notes.
- RawMaterialLedger is already used to calculate movements/balances; opening verification is represented through a ledger transaction and audit event.
- Required before activation: GET returns only real sheet master records; receive and verification reject unknown material IDs; only a separate Owner-authorized master-create action may add a master record; no seed fallback.

PRODUCTPRICES / PRODUCTTAXRULES / SALESCHANNELS / UNITSOFMEASUREMENT
- No corresponding route/model references found in inspected current main backend source.
- Physical sheets are generic 7-column placeholders.
- Keep deferred until schemas and API ownership are approved.

SALES INTEGRATION
- Sales routes accept actual_unit_price from the request; no ProductPrices lookup was found.
- Sale item stores actual_unit_price and snapshots SKU/product name/pack size.
- Sales routes contain hard-coded retail pack-size checks; a legacy order path also applies a fixed 5% tax calculation.
- Do not activate ProductPrices or ProductTaxRules until server-side price/tax lookup and immutable sale-line snapshots are implemented.

SHEETS ADAPTER
- append_record warns and silently omits record keys absent from physical headers unless authorize_header_update=True.
- API can therefore return success while some requested fields are not persisted.
- Before master-data activation, add strict header/field preflight: reject unknown record keys and missing required headers; never silently drop fields; no automatic header expansion by default.
- Verify every successful write by fresh read-back using the primary key.
- Do not allocate IDs before required-field, duplicate and reference validation.

Customers

RawMaterials
