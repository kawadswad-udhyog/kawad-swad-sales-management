3. CRITICAL FINDING DB-001 - MISSING SCHEMA COVERAGE FUNCTION
Severity: CRITICAL / P0
Evidence:
- backend/app/routers/v2_erp.py imports get_schema_coverage_summary from app.schema_registry.
- The supplied backend/app/schema_registry.py does not define get_schema_coverage_summary.
- Static import-symbol check confirmed the missing imported symbol.
- backend/app/main.py imports and includes the v2_erp router.
Impact:
- Application startup/import of v2_erp is expected to fail with ImportError before the application can serve requests.
- The schema-registry metadata endpoint also depends on this function.
Recommended correction:
- Restore/implement the function with accurate counts based on the current registry.
- Add an import/startup test that imports app.main and app.routers.v2_erp.
- Do not claim runtime readiness until this is fixed and verified.


4. CRITICAL FINDING DB-002 - CORE SCHEMA CONFLICTS ARE DOCUMENTED BUT NOT WRITE-GATED
Severity: CRITICAL / P0
Evidence:
- SCHEMA_HEADER_VARIANCES documents 12 core tables with CONFLICT_RECONCILIATION_REQUIRED.
- AppsScriptBridge.execute_governed_write blocks tabs in PENDING_OWNER_MAPPING_TABS (the 24 extended contracts).
- The bridge does not reference SCHEMA_HEADER_VARIANCES or apply a gate for those 12 core conflicts.
Impact:
- Core write actions can pass the schema-conflict gate even though their field/header contracts are explicitly marked unresolved in the registry.
- If the Apps Script implementation applies strict header mapping/pruning, fields not present in Row-1 may be omitted; if it writes differently, behavior remains unverified because the deployed Apps Script source is absent.
Recommended correction:
- Add a fail-closed policy for all CONFLICT_RECONCILIATION_REQUIRED core tabs.
- Allow writes only after owner-confirmed physical headers and an approved mapping.
- Add tests proving each conflicting table blocks writes until reconciliation is approved.

7. ID CONTRACT FINDINGS
Severity: HIGH / P1

7A. Legacy-to-locked prefix migration is still unresolved.
The code records 10 legacy-to-locked prefix aliases, including:
CUS -> CUST (Customers)
JRN -> JV (JournalHeaders)
JLN -> JVL (JournalLines)
PKG -> PKB (PackagingBatches)
PAY -> RCPT (Payments)
PRB -> PB (ProductionBatches)
PST -> MOV (ProductionStockLedger)
RWM -> RM (RawMaterials)
ITEM -> INVI (SaleItems)
SALE -> INV (Sales)
The owner/app-script cutover is still documented as pending.

7B. PKG historical collision.
Legacy ID_PREFIXES assigns PKG to PackagingBatches, while the locked v2 contract assigns PKG to PackagingMaterials and PKB to PackagingBatches. This is documented but remains a migration/read-compatibility risk until the Apps Script allocator and physical sheets are confirmed.

7C. Prefix validation gaps in action specs.
Static audit found 11 governed actions that require allocated IDs for tables with canonical locked prefixes but do not specify locked_prefix in their action specs. In those cases the backend validator skips prefix enforcement because the action spec has no locked_prefix.
Actions:
- CREATE_CUSTOMER (Customers / CUST)
- CREATE_RAW_MATERIAL_MASTER (RawMaterials / RM)
- ADJUST_FINISHED_GOODS_STOCK (ProductionStockLedger / MOV)
- CREATE_PRODUCTION_BATCH (ProductionBatches / PB)
- RECORD_PACKAGING_PENDING_REVIEW (PackagingBatches / PKB)
- RECORD_PACKAGING_BATCH (PackagingBatches / PKB)
- CREATE_SALE (Sales / INV)
- CREATE_SALES_INVOICE (Sales / INV)
- CREATE_LEGACY_SALES_ORDER (Sales / INV)
- RECORD_SALE_PAYMENT (Payments / RCPT)
- RECONCILE_FACTORY_STOCK (ProductionStockLedger / MOV)
Recommended correction:
- Add explicit locked-prefix validation to each applicable action.
- Document legacy aliases centrally and apply them only to the specific tables where migration compatibility is intended.
- Test canonical IDs, permitted legacy IDs, malformed IDs, and wrong-table IDs.
